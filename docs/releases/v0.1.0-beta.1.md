# OpenSend v0.1.0-beta.1 — draft release notes

OpenSend is a self-hostable, multi-tenant transactional email platform for developers, agencies and
SaaS teams. This first beta is intended for evaluation, local development and carefully monitored
self-hosting—not unattended production adoption.

## Highlights

- Organization → project → environment isolation, scoped API keys and team roles.
- Durable PostgreSQL acceptance with idempotency, transactional outbox and worker recovery.
- Local Mailpit, generic TLS SMTP and Amazon SES adapters.
- Recipient-level submission and provider-event tracking without conflating submission with delivery.
- Encrypted message content, attachments, provider credentials and webhook secrets.
- Templates, domains, signed webhooks, suppressions, quotas, retention, audit log and dashboard.
- TypeScript SDK plus generated OpenAPI 3.1 document.

## Supported installation methods

- Local pnpm + Docker infrastructure flow in `README.md` and `docs/SELF_HOSTING.md`.
- Docker Compose `app` profile building API, worker and dashboard images locally.
- Custom production deployment using the documented PostgreSQL, Redis and S3-compatible services.

No prebuilt container image or managed cloud service is published with this beta.

## Known limitations

- Amazon SES/SNS has test-double coverage but still requires a real-account verification run.
- Generic SMTP TLS/authentication requires verification against a real relay.
- DNS verification tests use a fake resolver; production DNS behavior is not automated end-to-end.
- Load, sustained throughput, large-dataset retention and disaster-recovery drills are not yet release evidence.
- The API and deployment model may change during beta; only the newest beta is supported.

## Upgrade considerations

This is the first planned release. Back up PostgreSQL, the object bucket and encryption keys before
every beta upgrade. Run database migrations before starting the new API/worker version and keep old
encryption keys configured until their retained attachments have expired. Review `.env.example`,
`CHANGELOG.md` and migration files for every upgrade.

## Security

Report vulnerabilities privately using GitHub Security Advisories as described in `SECURITY.md`.
Do not include credentials, recipient/customer data, message bodies or production logs.

The launch-readiness review covered authentication, API keys, tenant boundaries, encryption,
webhooks, SSRF, SMTP, quotas, logging, attachments, bootstrap, production configuration and
committed-secret risk. Seven scan-start findings were remediated and the full automated suite was
rerun successfully; see `docs/LAUNCH_READINESS.md` for exact evidence and limitations.
